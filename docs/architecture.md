# Architecture

[Português do Brasil](architecture.pt-BR.md)

`config` validates TOML and CLI overrides; `cli` dispatches backup, restore and verification with stable exit codes. `inventory` defaults to metadata-only size/mtime records; hash mode calculates fingerprints using validated cache entries and periodic full scans. Both detect concurrent metadata changes. `batches` is a pure planner: directories, oldest-first ordering, stable previous membership and profile boundaries. `profiles` maps filenames to separate text/video/photo/other settings.

`storage` implements inventory, upload, bounded bulk upload, exact download, metadata stat, historical preservation and deletion through rclone. `process` supplies bounded retries/timeouts and redacted errors without shell interpolation. `state` validates complete indexes, atomically writes private JSON and locks a single writer. `logging` writes private JSONL audits and redacts values before serialization. `notify` handles optional Cronitor telemetry.

`secrets` uses the [python-dotenv parser](https://github.com/theskumar/python-dotenv) to validate a whole file as data. Inherited environment variables take priority; no shell execution or parent-environment mutation occurs. The same private environment reaches dependency lookup and subprocesses. The internal environment field cannot be supplied through TOML or exposed by configuration representations.

`engine` coordinates per-job preflight and inventories, guards, strategies, summaries and periodic verification. Strategy plugins receive `Context`, with job/configuration, inventory, state, storage and log. New strategies/backends must extend configuration validation and the Storage contract.

Copy backups save preserved history before changing current files. Bounded bulk transfers use the selected size/time or checksum comparison, retain update protection and validate sources before and after the group. Batch keys are immutable and derived from original indexed metadata; the planner reuses compatible intact archives. Worker threads own separate subprocess state and staging. The main thread publishes the recovery index only after all uploads, then commits local state. Failure can leave immutable orphans, but never claims an incomplete new index. Retention cleanup uses `index_pending` to retry publication after failures.

`filtering` freezes rules and delegates matching to rclone, including historical paths represented by empty files. Results are cached per Selection per execution. Legacy mixed excluded batches stay in `excluded`. `retention` stores deadlines/original paths and aggregates advisory warnings; the separate removal guard blocks large inventory losses before strategy execution. `mounts` checks pinned nonempty volumes, and `disks` rejects local filesystems above 95% occupancy before backup and destination changes.

`recovery` restores literal paths from the active index into separate staging, validates sizes and any recorded hashes and safe archive members, then creates output files exclusively. It can read only `state.json` from a recovery tar without arbitrary extraction. Copy verification uses size/time by default or content/MD5 in hash mode. Archives and controls retain checksums in both modes. S3 verification only calls metadata stat and never downloads object bodies or missing indexes. Legacy archive controls without upload checksums fail verification explicitly. Only successful periodic checks update their timestamp.

`progress` displays throttled stage/directory/percentage updates only on interactive stderr. Inventory counters use files or bytes, discovery uses a directory-queue estimate, bulk rclone copies use the live transfer percentage, and other opaque subprocesses use a bounded elapsed-time estimate until completion. `logging` clears the transient line before printing JSON; progress has no audit event. Simple file records store paired empty hashes; switching to hash must re-read those contents.

The writer lock covers backup execution and manual verification. Restore reads an atomic index snapshot and fails if a concurrently retired object is unavailable. Without filesystem snapshots, concurrent source changes can interrupt a backup. Jobs are independently committed; there is no distributed transaction across jobs. Overlapping jobs follow TOML order and may invalidate each other's indexes or overwrite a shared remote recovery control; preserving local state and using dedicated prefixes avoids those interactions. Fingerprint reuse assumes honest local filesystem metadata; complete periodic scans are the fallback.
